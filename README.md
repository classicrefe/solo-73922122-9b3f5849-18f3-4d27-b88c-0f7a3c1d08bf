# 桥梁巡检单表包工具

档案员工作流程：巡检单入仓后，**测点清单**与**照片清单**被分表保存。本工具提供网页完成三件事：

1. **拆表**：上传巡检 JSONL（每行一张巡检单，单行 ≤ 64 KiB），按唯一巡检号拆成
   主表 / 测点表 / 照片表，三表以 JSONL 打成 ZIP 下载（表包内各表行序不限）。
2. **还原**：上传表包 ZIP，先校验整包（无主行、重复位置、缺位 / 多余明细等），
   **全部通过后才开放还原 JSONL 下载**；任一问题即整包退回并逐条列出问题。
3. **差异导出**：上传**基线表包**与**当前表包**，填写**导出单号**，按巡检号及
   测点 / 照片的稳定序号识别新增、修改、删除，输出可重放的增量 JSONL。

## 数据约定

巡检 JSONL 每行一个 JSON 对象：

| 字段 | 说明 |
| --- | --- |
| `inspect_no` | 巡检号，非空字符串，全文件唯一（必填） |
| `points` | 测点清单：数组 / `null` / 缺省 |
| `photos` | 照片清单：数组 / `null` / 缺省 |
| 其余字段 | 任意，全部进主表 |

表包 ZIP 固定三个成员（允许一层目录前缀），各表行序不限：

- `main.jsonl`：巡检单去掉两类清单后的全部字段，外加 `_meta`，例如
  `{"inspect_no":"JX-1", ...,"_meta":{"points":"list","points_len":3,"photos":"absent","photos_len":0}}`
- `points.jsonl` / `photos.jsonl`：`{"_no": 巡检号, "_seq": 原序号(0 起), ...清单项原字段...}`

`_meta` / `_no` / `_seq` 为保留字段。清单项必须是 JSON 对象。

## 差异导出格式

增量流按**巡检号升序**逐行输出，一个巡检单一行（一个变更组）；组内 `points` /
`photos` 按稳定序号 `seq` 升序。与表包内行序、ZIP 成员顺序无关，字节级可重放：

```json
{"inspect_no":"JX-2026-0001","change":"modified",
 "before":{"fields":{"inspect_no":"JX-2026-0001","bridge":"青云江大桥"},
           "lists":{"points":"list","photos":"list"}},
 "after": {"fields":{"inspect_no":"JX-2026-0001","bridge":"青云江大桥"},
           "lists":{"points":"list","photos":"list"}},
 "points":[{"seq":0,"change":"modified","before":{...},"after":{...}},
           {"seq":3,"change":"added","after":{...}},
           {"seq":4,"change":"deleted","before":{...}}],
 "photos":[...]}
```

- `change`：`added` / `modified` / `deleted`；未变化的巡检单不输出。
- 主记录变化写在 `before` / `after` 的 `fields`，两类清单的状态（`absent`/`null`/`list`）
  写在 `lists`，因此“缺省 → `[]`”“`null` → `[]`”等状态变化也会被判为修改。
- 明细变更只含 `seq`、`change` 及对应侧的 `before` / `after`。**删除项保留原值与序号**
  （只有 `before`），整单删除时其全部明细按原序号逐条列出。
- 值比较采用规范化 JSON（键排序、区分 `1` / `1.0` / `true`），不依赖 Python 的宽松相等。

### 退回与幂等规则

| 情形 | 结果 |
| --- | --- |
| 任一表包未通过整包校验（无主行、缺位 / 多余、重复位置、非法 `_meta`/`_seq`、缺表、非 ZIP…） | 422，**整单退回**，无下载；错误按 `baseline/`、`current/` 标明来源包 |
| 同一巡检号在同一明细表内序号重复（序号含糊） | 422，整单退回 |
| 导出单号缺失 / 空 / 含控制字符 / 超过 64 字符 | 400，不生成文件 |
| 同单号 + **内容相同**的两包（表内容规范化指纹一致，重新打包 / 打乱行序也算相同） | 200，返回**首次结果**（原 token、原统计、原 SHA-256），不重复计算 |
| 同单号 + 不同两包（换包） | 409，拒绝，无下载 |
| 首次导出失败 | 不占用单号，修好包后同单号可重新导出 |

单号登记持久化在工作目录的 `diff-registry.sqlite3`（WAL），多 worker / 重启后仍生效；
并发同单号请求由主键约束收敛为同一结果。

## 实现要点

- **忠实还原**：`_meta` 记录两类清单的状态（`absent`/`null`/`list`）与声明长度。
  还原时缺省的不补字段、`null` 的还原为 `null`、空列表还原为 `[]`；
  明细行携带 `_seq`，还原按序号排序，因此**两类清单各自的原顺序与表内行序无关**。
- **内存不随全包行数增长**（拆表、还原、差异导出均是）：
  - 全程逐行流式读写；上传分块落盘；ZIP 成员流式解压 / 压缩；
  - 巡检号去重、主从关联、聚合校验、差异归并全部放在 **SQLite 磁盘库**
    （`temp_store=FILE`，页缓存约 2 MiB），Python 侧只保留常数级状态；
  - 差异导出直接复用两包还原后的磁盘库（`ATTACH` 后按巡检号归并），不二次解包；
  - 单行有上限（巡检单 64 KiB；表包行 1 MiB 防御性限制），超长行截断跳过不载入内存；
  - 错误报告只保留前 200 条明细，总数与分类计数完整统计。
- **还原校验**（任一失败即退回整包，不产生下载链接）：
  - 无主行：明细行巡检号在主表不存在；
  - 重复位置：同一巡检号在同一明细表内 `_seq` 重复；
  - 缺位明细：实际序号集合未覆盖 `_meta` 声明的 `0..len-1`；
  - 多余明细：出现声明范围之外的明细（含清单为 absent/null 却有明细行）；
  - 结构错误：重复巡检号、非法 JSON、非法 `_meta`/`_seq`、主表夹带清单字段、缺表等。
- **拆表校验**：重复巡检号、行超长、非法 JSON、清单字段非数组、清单项非对象、保留字段冲突。

## 运行

### Docker Compose（推荐）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

Dockerfile 同时复制 `app/` 与 `examples/`（页面上的演示样例），数据落在 `appdata` 卷
（`APP_WORK_DIR=/data`），重建容器后导出单号登记与结果仍在。

### 本地开发

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/gunicorn --workers 2 --bind 127.0.0.1:8000 "app.web:create_app()"
```

### 页面演示（成功与退回）

1. 打开首页，在“③ 差异导出”下点“巡检 JSONL（基线）/（当前）”下载两份样例；
2. 分别经“① 拆表”生成基线表包与当前表包；
3. 基线包 + 当前包 + 导出单号（如 `EXP-2026-0001`）提交 → 成功页可下载增量 JSONL；
   再提交一次相同内容 → 显示“重放：返回首次结果”；
4. 换一个当前包、沿用同一单号 → 409 换包拒绝，页面无下载；
5. 用被篡改的表包（或任意非 ZIP）→ 422 整单退回，页面逐条列出问题分类。

### 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 三表单页面（拆表、还原、差异导出）及样例下载链接 |
| POST | `/split` | 表单字段 `file`：巡检 JSONL → 结果页（含表包 ZIP 下载链接） |
| POST | `/restore` | 表单字段 `file`：表包 ZIP → 校验通过才有还原 JSONL 下载链接 |
| POST | `/diff` | 表单字段 `baseline`、`current`、`batch_no`：两包均校验通过才有增量 JSONL 下载链接 |
| GET | `/download/<token>` | 下载结果文件 |
| GET | `/examples/<name>` | 下载页面演示样例（白名单） |
| GET | `/healthz` | 健康检查 |

POST 接口加 `?format=json`（或 `Accept: application/json`）返回 JSON，便于脚本集成。
`/diff` 的 JSON 额外含 `batch_no`、`replayed`、`baseline_sha256`、`current_sha256`
（表内容规范化指纹）、`result_sha256`、`notice`。成功响应 200，校验退回 422，
单号换包冲突 409，参数错误 400。
环境变量：`APP_WORK_DIR`（工作目录，默认系统临时目录）、`MAX_UPLOAD_BYTES`（上传总量上限，默认 1 GiB）。

## 测试与演示

```bash
.venv/bin/python -m unittest discover -s tests -v   # 48 项单元/接口测试
./scripts/demo.sh http://127.0.0.1:8000             # 端到端演示（拆表→还原→比对→错误注入）
./scripts/demo-diff.sh http://127.0.0.1:8000        # 差异导出端到端（成功→重放→换包拒绝→退回）
```

实测（本仓库交付前）：

- 48 项测试全部通过：
  - 原有 24 项：往返一致性（缺省 / null / 空列表原样保留）、表行乱序后清单顺序仍保持、
    无主行 / 重复位置 / 缺位 / 多余 / 重复巡检号 / 行超长 / 非法 JSON 等错误注入；
  - 新增 24 项：新增 / 修改 / 删除变更组、删除项保留原值与序号、整单新增 / 删除的明细展开、
    空增量流、类型变化（`1` vs `1.0` vs `true`）、元数据状态变化、两包行序打乱与重新打包后
    输出字节一致、坏包 / 无主行 / 重复序号整单退回、错误来源包标注、单号校验与登记、
    Web 页面（HTML + JSON）成功 / 重放 / 换包 409 / 退回 422 / 缺单号 400、样例白名单。
- 内存冒烟：20,000 张巡检单拆表与还原 Python 侧峰值 < 1.2 MiB；
  4,000 张巡检单的差异导出峰值约 1.2 MiB（SQLite 状态落盘）。
- `scripts/demo.sh` 全流程通过（拆表 → 还原 → 逐字段语义一致 → 坏包 422 无下载）。
- `scripts/demo-diff.sh` 全流程通过：4 个变更组（1 修改 / 1 删除 / 1 状态变化 / 1 新增），
  删除项保留序号与原值；同单号相同两包重放字节一致；换包 409；注入“无主行 + 重复序号”
  的坏包 422 且无下载；失败不占单号。
- 并发实测（gunicorn 2 worker，20 并发）：同一单号相同两包收敛为 1 个 token（19 次重放）；
  同单号混合两套包得到 10×200 + 10×409，409 均无下载。
- 页面实测（真实 HTTP）：成功页含下载链接与单号 / 双包指纹、重放提示、换包拒绝、坏包退回均正确。

## 限制与未完成项

- 本环境未安装 Docker，`docker compose up` 未实际执行；Dockerfile / compose 配置经静态核对，
  应用本体以与 Dockerfile 相同的 gunicorn 命令（2 worker）实测通过。
- 差异判定是**按序号逐位比较**：明细中间插入一条会使其后所有序号都判为修改（数据约定
  `_seq` 是稳定序号，不提供基于内容的多重集匹配）。
- 还原输出的记录顺序按主表行序（表包不携带原始上传顺序）；对象内 `points`/`photos`
  键固定在末尾；数字等 JSON 文本表示可能变化（语义不变）。
- 结果文件与单号登记无 TTL 清理（`/download/<token>` 长期有效，token 不可猜测）；
  未做鉴权与多用户隔离；登记库与结果文件需同时保留，结果被删除时同单号会重新计算。
- 同步处理，超大包会占用单个请求的工作进程（未引入任务队列）。
- 表包行上限 1 MiB、错误报告展示上限 200 条为硬编码常量（`app/core.py`）。
